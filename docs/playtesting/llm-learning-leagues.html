LLM learning leagues

How persistent language-model players play, explain, share lessons, and adapt across a sequence of complete games.

Index/LLM learning leagues
Ruleset-21 process

What this is

An LLM learning league uses persistent language-model identities as the players. Each identity receives its own private game projection, reasons about strategic choices, submits those choices through the authenticated game API, and explains its result after the complete replay becomes available. Before the next game, every player receives the cumulative shared lessons from all earlier games.

This is not reinforcement learning. There are no learned weight vectors, value functions, reward updates, exploration schedules, or automated policy checkpoints. It is also not a fixed heuristic simulation: mechanical tooling may fetch state, enumerate legal inputs, and submit a selected command, but an LLM must choose the strategic action.

Predeclare the league

  1. Record the code commit, ruleset, player count, number of games, and primary design questions.
  2. Create one persistent identity per player. Keep the identity, strategic style, private notes, and cumulative record stable across games.
  3. Start with only lessons that still apply to the current rules and map. Mark older observations as historical instead of silently treating them as current facts.
  4. Choose a deterministic seat rotation before Game 1. Over a complete rotation, each identity should occupy every seat equally; otherwise report the exact imbalance.
  5. Use a durable SQLite database and allow observers. Preserve every invitation code and authenticated player session before starting.

Give each LLM the right context

At the start of every game, give each player the current rules, map and card references, its seat and private projection, its own prior postmortems, and the complete shared learning dossier. Do not reveal another player’s hidden agendas, exact hand, held Bonus cards, or bearer token.

Private scoring cards are projected by ID, so the player must resolve those IDs against the current scoring-card reference. The player should plan for all three fixed agendas, while weighting the next Election most heavily. Public final-card counts are legitimate information; opponents’ exact card composition is not.

Play every game without shortcuts

  1. Create or join the lobby through the API, persist the returned session, and verify every intended player has joined before readying and starting.
  2. On each decision, fetch the acting player’s fresh private state. Use the projected version when submitting the command.
  3. Let the LLM compare the meaningful legal alternatives and choose. Legal-action enumeration may be automated; strategic scoring and selection may not be delegated to a fixed heuristic.
  4. After each Operation card, refetch state and let the same LLM decide whether to finish or play another card. Never precommit a multi-card sequence against stale state.
  5. Let the owning LLM decide every optional Bonus award, automatic Closure choice, voluntary Close, Collect, and Pass. Do not decline or skip choices for speed.
  6. Continue through all six years and all three Elections. A player acknowledges an Election only after inspecting its result.

No pacing constraints: there is no time limit. Do not cap Operation length, force passes, skip counterplay, suppress Bonus choices, or alter strategy to finish sooner. Parallel controllers reduce waiting; they do not change the rules.

Learn after every game

  1. Make the completed replay available to all players.
  2. Ask each identity for a first-person explanation of why it won or lost, citing its agendas, timing, map position, card economy, Bonus choices, final-card rank, and decisive opponent actions.
  3. Require a small number of concrete lessons and intended changes. Separate observed facts from interpretation.
  4. Combine all four postmortems into the cumulative shared dossier without erasing disagreements. Deduplicate repeated lessons and retain the game that supplied each one.
  5. Give the updated dossier to every identity before the next game. Preserve identity-specific adjustments privately as well.

Learning is prospective: a lesson affects only later games. Do not rewrite an earlier decision as though the player already knew its result.

Record enough evidence

  • Invitation code, seat order, ruleset, final scores, Election breakdowns, winner, and final ordinary-plus-held-Bonus card counts.
  • Every accepted and rejected API command, Operation bundle length, Collect size, Closure cause, Pass, Bonus award, and Bonus play.
  • Each player’s complete postmortem, proposed changes, and the dossier supplied to the next game.
  • Patterns by player, seat, game cohort, action family, agenda conversion, card circulation, and final-card ranking.

Keep the canonical SQLite replay. The written report should be sufficient to understand the findings, but summaries cannot replace the event history when a surprising interaction needs verification.

Interpretation limits

  • Later games are not independent samples: all players share prior lessons and adapt together.
  • An LLM explanation is evidence about its reasoning, not proof that the claimed cause decided the outcome. Check claims against the replay.
  • Seat, agenda deal, Election draws, accumulated lessons, and model variability can all change at once.
  • Use repeated leagues or fixed non-learning comparison games before drawing balance conclusions.
  • Report facilitator interventions, rejected commands, lost sessions, or automated substitutions; any of them can invalidate strategic evidence.

Recommended handoff

A completed league should leave three durable artifacts: the database containing every replay, one session report with all results and player postmortems, and a compact current-rules dossier suitable for the next league. Record obsolete lessons separately instead of carrying them forward after a rules or map change.
